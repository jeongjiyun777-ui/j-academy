# 제이 외국어 온라인 학원

[한국어](README.md) | [English](README.en.md)

**학생의 회원가입부터 수강신청, 관리자의 승인과 엑셀 정리까지 연결한 외국어 학원 관리 포트폴리오입니다.**

Next.js와 FastAPI, PostgreSQL을 사용해 혼자 기획하고 개발했습니다. 학원 소개 페이지에 그치지 않고, 학생과 관리자가 서로 다른 역할로 같은 데이터를 사용하는 서비스를 만드는 것이 목표였습니다.

> 현재 가족 등 소규모 사용자에게 보여 주며 외부 접속과 모바일 동작을 점검하는 단계입니다. 실제 학원의 운영 실적을 가진 서비스는 아닙니다. 상담 화면은 구현되어 있으며, 현재 생성형 AI 답변 대신 과목·수준별 준비 중 안내를 제공합니다.

## 어떤 서비스를 만들었나요?

학생은 영어·스페인어·일본어·중국어의 담당 교사를 살펴보고 과목과 반을 신청합니다. 관리자는 신청 내역을 확인하고 승인 상태를 변경하며, 학생 목록과 문의 내용을 엑셀로 내려받습니다.

이 과정에서 반복되는 명단 정리와 수강 상태 확인을 줄이고자 했습니다. 화면을 만드는 것뿐 아니라 **입력한 데이터가 저장되고, 다른 권한을 가진 사용자에게 필요한 형태로 다시 보이는 과정**을 직접 구현했습니다.

## 주요 기능

| 구분 | 구현 내용 |
| --- | --- |
| 회원가입 | 필수 입력에 따른 버튼 활성화, 서버 입력값 검증, 아이디·전화번호 중복 제한 |
| 로그인 | JWT 기반 인증, 학생·관리자 역할 구분, 보호된 API의 서버 권한 검사 |
| 계정 찾기 | 가입 정보 기반 아이디 찾기 및 마스킹, 계정 정보 확인 후 비밀번호 변경 |
| 수강신청 | 과목·반 선택, 신청 내역 조회, 승인대기·승인완료 상태 관리 |
| 학생 관리 | 이름 검색, 20개 단위 페이지 조회, 페이지 내 행 번호 표시 |
| 신청 관리 | 승인대기 목록 페이지 조회, 선택한 신청의 상태 일괄 변경 |
| 업무 자동화 | 학생 목록·문의 목록 엑셀 다운로드와 순번, 회원가입·수강신청·문의 이메일 알림 연동 |
| 상담 화면 | 승인된 과목·반 선택, 학생별 인사말, 과목·수준을 반영한 안내 응답 |
| 소개 화면 | 학원 소개, 언어별 담당 교사, 수강평 소개 화면 |
| 모바일 UI | 터치로 여닫는 메뉴, 좁은 화면에서 표 가로 스크롤, 입력 폼과 채팅 UI |

전화번호 중복 제한은 **동일 번호의 중복 가입을 막는 규칙**이며, 휴대폰 소유자 본인인증을 의미하지는 않습니다. 비밀번호 재설정은 현재 가입 정보 대조 방식으로, 일회성·만료 토큰을 통한 검증은 후속 개선 항목입니다.

## 데이터가 흐르는 방식

```text
사용자 입력
  → React 상태 업데이트와 입력 확인
  → fetch로 FastAPI에 요청
  → 입력값·JWT·역할 확인
  → PostgreSQL 조회 또는 변경
  → JSON 응답
  → 목록·승인 상태·안내 문구 갱신
```

학생이 신청한 데이터는 관리자 승인 화면에 나타나고, 승인된 신청은 학생의 수강 정보와 상담 과목 선택에 반영됩니다. 보호된 요청에는 Bearer 토큰을 전달하며, 버튼을 숨기는 것과 서버에서 권한을 검사하는 것을 구분했습니다.

## 이 프로젝트에서 제가 가장 많이 붙잡았던 병목

처음에는 기능 하나가 고장 나면 어느 파일을 고쳐야 하는지부터 막막했습니다. 이 프로젝트를 만들면서 가장 많이 반복한 질문은 “지금 막힌 지점은 화면인가, 요청인가, 서버인가, DB인가?”였습니다. 그 질문을 기준으로 문제를 쪼개고, 확인한 사실을 바탕으로 다음 수정으로 넘어가려 했습니다.

특히 다음 병목을 끝까지 확인했습니다.

- **여러 과목 데이터:** 한 학생이 신청한 과목 중 하나만 챗봇에 보이던 문제를 조회 결과 구조부터 바꿔 해결했습니다.
- **관리자 목록:** 버튼만 있는 페이지네이션이 실제 목록을 바꾸지 못한다는 점을 확인한 뒤, API의 `LIMIT`·`OFFSET`·전체 건수와 프론트엔드 요청을 함께 연결했습니다.
- **권한과 안내:** 401·403·422 응답을 단순 오류로 남기지 않고, 로그인 필요·승인 필요·입력값 문제를 사용자가 이해할 수 있는 문구로 바꿨습니다.
- **외부 접속:** `Failed to fetch`를 토큰 문제라고 단정하지 않고, 브라우저 요청과 실제 응답을 비교해 터널의 경고 HTML이 JSON 응답을 가로채고 있음을 확인했습니다.
- **모바일 사용성:** hover에만 있던 메뉴를 터치 가능한 상태 변경으로 바꾸고, 넓은 표는 정보량을 버리지 않으면서 가로 스크롤로 대응했습니다.

문제가 생길 때마다 결과만 고치기보다 데이터가 움직이는 경로를 따라가려 했습니다. 이 태도는 아직 부족한 부분이 많은 주니어 개발자인 저에게 가장 중요한 기반이 되었습니다.

## 작은 입력 폼에서 시작한 개발 과정

### 1. 입력값 하나를 DB에 저장하기

처음에는 `input`의 `value`와 `onChange`, JSON의 역할도 익숙하지 않았습니다. 디자인이 거의 없는 입력 폼에서 값을 받아 DB에 저장하는 것부터 연습했습니다.

Make 웹훅을 다루며 데이터를 구조화해 주고받는 방식을 배웠고, 이를 React 상태 → API 요청 → DB 저장 → 응답 표시의 흐름으로 연결했습니다. 각 기능의 코드를 외우기보다 데이터가 어디에서 생겨 어디로 이동하는지 이해하려 했습니다.

### 2. 학생과 관리자의 업무 연결하기

회원가입과 로그인에 이어 수강신청, 승인 상태, 목록 검색, 상담 접근 조건을 추가했습니다. 프론트엔드에서 보이는 화면과 백엔드가 실제로 허용하는 작업이 다를 수 있다는 점을 배우면서 JWT와 역할 검사를 적용했습니다.

### 3. 관리자가 읽고 정리할 수 있는 데이터 만들기

목록이 늘어나자 페이지네이션과 행 번호가 필요해졌습니다. 웹에서는 한 페이지의 항목을 쉽게 셀 수 있도록 1부터 번호를 표시하고, 엑셀에서는 내려받는 전체 목록에 연속 번호를 부여했습니다. 같은 데이터라도 사용 목적에 따라 표시 방식이 달라진다는 점을 배웠습니다.

### 4. 내 컴퓨터 밖에서 테스트하기

로컬에서 작동하던 기능을 휴대폰과 다른 네트워크에서 확인하면서 주소, 포트, CORS, 터널 응답, 모바일 브라우저 차이를 경험했습니다. 이 단계에서 “내 컴퓨터에서 보인다”와 “다른 사람이 사용할 수 있다”의 차이를 체감했습니다.

## 시행착오와 해결 과정

### 여러 과목을 신청했는데 하나만 보이던 상담 화면

단일 결과를 전제로 한 조회 방식으로는 여러 수강신청을 표현할 수 없었습니다. 조회 결과를 `.all()`로 받고, 프론트엔드가 과목·반 목록을 표시하도록 바꿨습니다. 학생이 선택한 과목을 상담 안내에 반영하면서 DB 조회 결과와 화면 데이터 구조를 함께 수정하는 경험을 했습니다.

### 페이지 버튼과 실제 데이터 조회의 차이

이전·다음 버튼만 만들어서는 서버가 보내는 목록이 달라지지 않았습니다. 백엔드에서 `LIMIT 20`, `OFFSET = (page - 1) * 20`과 전체 건수 조회를 적용하고, 프론트엔드에서는 페이지 번호를 요청에 전달했습니다. 조회 함수를 `useEffect` 밖으로 옮겨 최초 로딩과 페이지 이동에서 재사용했습니다.

### 전화번호 중복 가입이 서버 오류로 보이던 문제

DB의 중복 제한에 맞춰 API에서도 중복 여부를 확인하고, 무결성 오류를 `409 Conflict`로 처리했습니다. 프론트엔드는 서버의 안내를 표시하도록 연결했습니다. DB 규칙, API 상태 코드, 사용자가 읽는 메시지를 하나의 흐름으로 맞추는 작업이었습니다.

### 관리자 목록의 `Failed to fetch`

외부 접속에서 학생 기능 일부는 작동했지만 관리자 목록은 실패했습니다. 처음에는 주소와 CORS 설정을 의심했으나, 응답을 비교하면서 ngrok이 일부 GET 요청에 API의 JSON 대신 경고 HTML을 반환하는 상황을 확인했습니다.

터널 경고를 건너뛰는 요청 헤더를 적용하고 백엔드의 허용 헤더도 맞췄습니다. 이 경험을 통해 **브라우저에 CORS 오류가 보인다고 해서 원인이 항상 CORS 설정인 것은 아니라는 점**을 배웠습니다. 요청이 어디까지 도달했고 어떤 응답이 돌아왔는지 확인하는 것이 중요했습니다.

### 모바일에서는 눌리지 않던 메뉴와 넓은 표

마우스 hover를 전제로 한 메뉴를 React 상태와 클릭 이벤트로 여닫도록 개선했습니다. 관리 표는 내용을 무리하게 줄이는 대신 가로 스크롤을 활용했습니다. 화면 크기뿐 아니라 터치와 마우스의 사용 방식도 고려하게 되었습니다.

### iOS hydration 경고 점검 — 진행 중

서버 HTML과 브라우저의 첫 렌더링이 다르다는 경고를 확인했습니다. 프론트엔드 33개 TSX 파일의 대표적인 태그 중첩과 초기 렌더링 관련 코드를 점검하고, 공통 레이아웃에 iOS의 전화번호·날짜·이메일·주소 자동 링크 변환 방지 설정을 추가했습니다.

수정 후 TypeScript 검사는 통과했지만, 해당 경고의 최종 원인과 실제 기기에서의 해소 여부는 추가 확인이 필요합니다. 아직 확인하지 않은 문제를 해결 완료로 기록하지 않으려 합니다.

## AI와 함께 개발하며 배운 점

AI의 도움으로 코드 초안, 오류 설명, 수정 방향을 얻었습니다. 동시에 코드를 직접 수정하고 요청·응답·DB 데이터를 확인하며, 제 서비스에서 왜 동작하는지 이해하려 했습니다.

초기에는 생성된 코드를 적용한 뒤 화면이 깨지면 어디서부터 살펴봐야 할지 막막했습니다. 이후에는 입력 상태, 이벤트, 요청 주소, 응답 상태, DB 조회를 나누어 살펴보는 방식으로 바뀌었습니다. 가장 큰 성장은 기능의 개수보다 **문제가 발생한 위치를 좁히고 수정 이유를 설명할 수 있게 된 것**입니다.

이 프로젝트는 혼자 모든 것을 이미 안다는 증명이 아니라, 작은 기능부터 배우고 시행착오를 기록하면서 하나의 서비스로 연결한 결과물입니다. 처음에는 입력 폼 하나도 낯설었지만, 화면이 깨지고 요청이 실패할 때마다 포기하지 않고 원인을 찾아 다시 고쳤습니다. 기능이 작아 보여도 사용자가 실제로 누르고, 막히고, 다시 시도하는 순간까지 생각하며 완성도를 높이고자 했습니다.

저는 아직 배우는 단계이지만, 모르는 문제를 만났을 때 피하지 않고 직접 재현하고, 로그와 응답을 확인하고, 끝까지 연결해 보는 개발자가 되고 싶습니다. 이 서비스에 담긴 가장 큰 가치는 기능의 개수보다 그 과정에서 쌓은 집요함과 책임감이라고 생각합니다.
