# J Online Academy | 외국어 학원 업무 관리

[한국어](README.md) · [English](README.en.md) · [日本語](README.ja.md)

[서비스 보기](https://j-academy-two.vercel.app/) · [시연 영상](https://www.youtube.com/watch?v=_D9eecQplGM)

학생의 가입과 수강신청을 받아 관리자의 승인, 명단 정리, 이메일 알림까지 연결한 웹 서비스입니다. 정지윤이 기획부터 화면·서버·DB 개발과 배포까지 진행한 개인 포트폴리오입니다.

별도 설치 없이 [배포된 서비스](https://j-academy-two.vercel.app/)에서 사용할 수 있습니다. [로그인 화면](https://j-academy-two.vercel.app/login)에서 아래 계정으로 기능을 확인해 주세요.

| --- | --- | --- |
| 관리자 | `admin1234@naver.com` | `ab#12345678` |

공용 체험 계정입니다. 실제 개인정보는 입력하지 말아 주세요. 다른 체험자의 작업으로 데이터가 달라질 수 있으며, 무료 서버의 첫 응답은 시간이 걸릴 수 있습니다.

## 시스템이 대신 하는 일

학생이 과목과 반을 신청하면 신청서가 DB에 저장되고 관리자 화면에 나타납니다. 관리자에게 이메일 알림도 보냅니다. 관리자가 승인하면 학생의 수강 정보에 반영됩니다. 직원이 신청서를 다시 옮겨 적거나 명단을 따로 만들 필요를 줄이는 구조입니다. 승인 판단은 관리자가 합니다.

`학생 신청 → DB 저장 → 관리자 알림·목록 → 승인 → 학생 화면 반영`

## 주요 기능

- 회원가입, 아이디 중복 확인, 아이디 찾기와 비밀번호 변경
- 비밀번호 해시, 학생·관리자 권한 검사, JWT 로그인과 리프레시 토큰
- 과목·반 신청, 중복 신청 제한, 신청 상태 조회와 관리자 일괄 승인
- 학생 검색, 학생·신청 목록 페이지네이션, 학생·문의 목록 Excel 다운로드
- 회원가입·수강신청·문의 접수 시 관리자 이메일 알림
- 모바일 메뉴·표 스크롤, 학원·교사 소개, 승인된 수강 정보에 따른 상담 안내

## 문제를 해결한 방법

| 문제 | 수정한 내용 |
| --- | --- |
| 신청한 여러 과목 중 하나만 표시 | 여러 행을 조회하고 화면도 목록으로 표시하도록 연결 |
| 페이지 버튼을 눌러도 같은 목록 | 서버의 전체 건수·LIMIT·OFFSET과 화면의 페이지 요청을 연결 |
| 로그인 시간이 지나면 사용이 끊김 | DB에 해시로 저장한 리프레시 토큰과 HttpOnly 쿠키로 갱신·로그아웃 구현 |
| 배포 후 메일 발송 실패 | SMTP 방식에서 Brevo HTTPS API로 전환하고 발신자·관리자 수신 주소 분리 |
| 어두운 기기 설정에서 입력·선택 글자가 안 보임 | 흰 화면에 맞춰 색상 모드를 고정하고 입력 가독성 보완 |
| 로컬에서는 작동하지만 외부 요청 실패 | API 주소·CORS·실제 응답을 확인하고 Vercel과 Render 연결 설정 정리 |
| 개인정보가 디버그 로그에 남음 | 프론트 디버그 로그 제거, 민감한 응답의 캐시 제한 |

## 문제를 좁혀 가며 개발한 과정

수강신청 화면을 만드는 데서 끝내지 않고, 학생이 보낸 값이 DB에 저장되고 관리자 승인 후 다시 학생에게 보일 때까지 연결했습니다. 문제가 생기면 입력 상태 → 요청 주소·JSON → 응답 코드 → SQL·DB 결과 순서로 확인했습니다. 여러 과목 중 하나만 표시되는 문제는 조회 결과와 화면의 자료 구조를 함께 고쳤고, 페이지네이션은 버튼 모양보다 실제 조회 범위가 바뀌는지 확인했습니다. 로컬 구현 후에도 배포 주소, 인증 쿠키, 메일 전송, 모바일 입력을 다시 점검하며 수정했습니다.

## 기술과 배포 구성

Next.js 16 · React 19 · TypeScript · Tailwind CSS / Python · FastAPI · Pydantic / PostgreSQL · SQLAlchemy / JWT · pwdlib / pandas · openpyxl · BackgroundTasks · Brevo

- **Vercel**: 사용자가 보는 화면. `NEXT_PUBLIC_API_BASE_URL`로 Render API 연결.
- **Render**: 인증·수강신청·관리 업무 처리. Brevo API로 이메일 요청.
- **Neon**: 회원·신청·문의·토큰 데이터 저장.

`frontend/`: 화면 · `backend/main.py`: API·권한·DB 처리 · `backend/발송시스템.py`: 이메일 · `db/`: 스키마

### Linux 병목 분석 학습 — 2026-11-06

- 서버가 느릴 때 바로 증설하기보다 원인을 나눠 확인하는 접근을 학습했습니다. [`vmstat`](https://man7.org/linux/man-pages/man8/vmstat.8.html)의 CPU 시간 비율(`us/sy/id`), 실행 중·실행 대기 프로세스(`r`), 스왑 활동(`si/so`), I/O 대기 징후(`wa/b`)를 공부했습니다.
- 필요한 경우 `top`, `free`, `iostat`와 요청 로그·SQL·외부 API 응답을 함께 확인하고, 개선 전후를 Locust로 비교하는 검증을 진행할 계획입니다.
- 현재는 명령과 지표의 의미를 학습한 단계이며, 운영 서버의 병목을 확정하거나 성능 개선을 입증한 것은 아닙니다. 로컬 `vmstat` 값과 원격 Render 서버의 자원 지표도 구분합니다.

#### 메모리 여유와 스왑 활동 — 2026-11-08

`free -h`의 `Mem:` 행에서 `available`은 스왑 없이 새 작업에 내줄 수 있는 메모리의 추정치입니다. `free`가 작아도 회수할 수 있는 캐시가 있으면 `available`에는 여유가 있을 수 있습니다.

`vmstat`의 `si`와 `so`는 각각 스왑에서 RAM으로 읽어오는 양과 RAM에서 스왑으로 내보내는 초당 데이터량을 보여줍니다. 다음 Locust 테스트에서는 `available`이 줄고 스왑 활동이 이어지는 시점에 API 응답 시간도 늘어나는지 비교할 계획입니다.

## 수강 결제 설계와 학습 — 2026-11-12

- **현재** — PostgreSQL에 적용할 강좌·주문 스키마를 작성했습니다. 기초 12만 원, 중급 15만 원, 고급 18만 원이며, 주문은 생성 당시 금액과 `결제대기` 상태를 기록하도록 설계했습니다. [SQL 스키마](db/courses_orders.sql)
- **멱등성의 본질** — 프론트가 같은 결제 요청을 10번 보내도 결제는 한 건만 처리해야 합니다. 같은 주문의 같은 결제 시도에는 동일한 멱등성 키를 사용합니다. 이미 성공한 요청이면 서버가 저장된 결과를 반환합니다. 처리 중인 요청은 진행 중임을 응답하고, 같은 키에 다른 요청 내용이 들어오면 충돌로 처리할 계획입니다.
- **다음 구현** — Spring Boot에서 DB의 수강료로 주문을 만들고, 모의 결제부터 연결할 계획입니다. DB 고유 제약과 트랜잭션으로 동시에 도착한 요청 중 한 건만 처리 권한을 얻도록 설계하고, 실제 결제 연동 단계에서는 PG가 지원하는 멱등성 키와 결제 결과 조회도 활용할 예정입니다.
- **Locust 검증 계획** — 테스트 환경에서 같은 키로 10개 동시 요청을 보내 결제 기록이 한 건인지 DB에서 확인합니다. 서로 다른 주문도 함께 부하를 걸어 p95 응답 시간, 실패율, 처리량, DB 락 대기와 커넥션 풀 사용량을 비교합니다. 측정 결과를 보고 타임아웃과 동시 처리 한도를 조정할 계획입니다. 결제 API 구현과 결제 부하 측정은 예정 단계입니다.

### Spring Boot 회원 인증 실습

- **서버 실행** — `main()`에서 `SpringApplication.run()`을 호출해 서버를 시작했습니다. `@SpringBootApplication`은 앱 구성의 시작점을 지정하고, `import`는 코드에서 사용할 클래스와 애너테이션의 이름을 가져옵니다.
- **요청의 두 방향** — `@RestController`의 `@GetMapping("/checkout/session")`은 Java가 요청을 받는 입구입니다. 메서드 안의 `RestClient`는 Java가 받은 Bearer 토큰을 기존 FastAPI의 `/me`에 보내는 도구입니다. `private final` 필드로 두어 컨트롤러 안에서 같은 클라이언트를 재사용했습니다.
- **실패 경로와 반환값** — Java의 `try/catch`는 Python의 `try/except`와 같은 역할을 합니다. `catch`는 예외가 났을 때 실행할 경로를 정하고, `return`은 응답을 돌려줍니다. 토큰을 확인할 수 없는 경우 중 인증 서버 장애는 `502`, 토큰 누락·거절은 `401`로 처리합니다.
- **직접 확인한 결과** — PowerShell에서 로컬 Java 서버를 토큰 없이 호출해 `401`과 `WWW-Authenticate: Bearer`를 확인했습니다. 임시 인증 서버를 사용한 별도 테스트에서는 학생 `200`, 관리자 `403`, 누락·오류 토큰 `401`을 검증했습니다.
- **다음 실습** — 실제 HttpOnly 쿠키로 FastAPI `POST /refresh`를 호출하고, 발급된 액세스 토큰을 메모리에서 Java에 전달해 학생 ID가 돌아오는지 확인할 예정입니다. 이후 DB에서 수강료를 읽고 결제 대기 주문을 저장하는 기능을 붙일 계획입니다.

### 강좌 가격 조회와 주문 설계

- **가격의 기준은 DB입니다.** `payment-api`의 `GET /checkout/courses`가 PostgreSQL의 `public.courses`를 조회합니다. `JdbcTemplate`으로 SQL을 실행하고, 각 행을 `Course` 객체로 변환해 JSON으로 반환합니다.
- **확인한 결과** — 로컬 Spring Boot를 실행해 `200 OK`와 강좌 12건을 확인했습니다. 영어 기초반은 `priceKrw: 120000`으로 반환됐습니다. 이 API는 공개 강좌와 수강료를 조회합니다.
- **DB 설정** — 로컬에서는 기존 Python 백엔드의 `.env`에서 DB 접속값을 읽어 Spring Boot 환경 변수로 전달합니다.
- **다음 단계** — 학생 권한을 확인한 뒤, 받은 `courseId`로 DB 가격을 읽어 `결제대기` 주문에 금액을 저장할 계획입니다. 이후 모의 결제와 멱등성 검증을 붙입니다.

## 범위와 남은 개선

학습·포트폴리오 서비스입니다. 실제 개인정보 대신 테스트 데이터를 사용해 주세요. 상담 화면은 외부 AI를 호출하지 않고 준비된 안내를 제공합니다. 가입 정보 대조는 휴대폰 본인인증이 아니며, 비밀번호 재설정에는 일회성 인증 수단이 추가로 필요합니다. Render 무료 서비스는 첫 접속이 늦을 수 있고, 이메일 접수 응답은 받은 편지함 도착을 보장하지 않습니다. 실제 운영 전에는 계정 복구·요청 제한·실기기 검증을 보강해야 합니다.
